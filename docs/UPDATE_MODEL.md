# Update model

Raspberry Pi OS, HYDRA-UMC packages, Hailo runtimes/models, and MCU/URTC
firmware have separate update channels. They are never represented as one
opaque binary.

HYDRA-UMC artifacts require a manifest with version, compatibility, hash, and
signature. Before any future CM5 deployment flow changes a checkout, its
candidate manifest must validate, identify the same project, and not declare a
lower version than the installed manifest. The updater checks the target device
and dependency range, installs the candidate, restarts only required services,
and evaluates health. A failed health check must surface an actionable fault
and use rollback where supported. This is a deployment contract; it does not
claim that a rollback has been exercised on a CM5 before hardware testing.

**Status.** The paragraph above describes the target contract. Today no component
implements it end to end: the installers (`provisioning/install_*.sh`) copy a
checkout into place and restart its unit without a signed manifest, a
dependency-range check, a health gate or an automatic rollback, and
`tools/package_component.py` only packs and verifies signed component archives.
Read it as the direction of the work, not as a description of what runs on a
device.

**Built, not yet on a device.** `tools/deploy_release.py` is the core of that flow, tested in
temporary folders: it verifies a signed package, refuses the same or an older version, installs it
as a numbered release, switches `current`, runs the restart and health commands of
`<root>/deploy.json`, puts the earlier release back (exit status 3) when either fails, and offers
`rollback`, `prune` and `status`. No installer calls it yet and no rollback has been exercised on a
CM5.

**Started from Studio, built and checked on the host only.** HYDRA-UMC-SERVER can run that same flow for the user of Studio (`/api/admin/self-update`, off by default): it fetches `hydra-<component>-<version>.tgz`, its `.sha256` and its `.sig` from the newest release of the repository of the program, has `tools/package_component.py verify` check them (it prints one `PACKAGE=OK <component> <version> <sha256>` line, or `PACKAGE=REFUSED` on the error output with status 1), and starts `tools/deploy_release.py install` detached, with its output in a file, because restarting the server kills whatever the server started: the server reads the file for the last line, `DEPLOY=PASS` on the standard output or `DEPLOY=FAIL <reason>` on the error output (status 2 refused, 3 went back to the release that was in use), and the state of the component for the version in use. Both lines are part of the contract of the tool and `tools/verify_deploy_release.py` checks them. Only the unit of the component named in `restartCommand` is restarted (for example `systemctl try-restart hydra-umc-{component}` with a rule that lets the account of the server run exactly that), never the machine. What is not done yet: the units still run from `/opt/hydra-umc/<component>` and not from `<root>/<component>/current`, and no rule of sudo exists for that restart, so on a device this flow is not wired; it has not run on a CM5.

**Every installed program from Studio, built and checked on the host only.** `tools/fleet_update.py` brings the programs under `/opt/hydra-umc` to the newest published release, one at a time, in the order of their dependencies (the tools of this repository and the SDK as checkouts, the services from the leaves to the orchestration, the server last with its frontend). `plan` only looks; `run --yes` applies; `resume --yes --only <program>` takes up a program whose step was cut; `status` reads the file. The progress is a file (`hydra-fleet-update/1`, written atomically at every step, with a heartbeat file beside it), so the server that started it can restart in the middle and Studio still sees where it is. For each program: free disk (more for the server, which is built on the device), the tag fetched and its commit compared with the one GitHub gives (and `git verify-tag` for the programs of the list `signedTags` of the settings, by default the tools of this repository, the OS agent, the server with its Studio and the critical services, or for all of them with `requireSignedTags`), a `.tgz` of the program in use (one exact name, `<name>.bak.tgz`, kept as it was when the program is cut and taken up again) together with its unit and drop-ins and a hash of each, the build of the server in named steps, the installer of `provisioning/` with `--apply` (it restarts that unit only), then the checks: version, unit active, health route, no import error or missing file in the journal, and the Python SDK importable by the unit. A failure puts the `.tgz` back, removes the drop-ins the installer added, reloads systemd and says whether the unit files are as they were (`unitRestored`); the run stops there. A cut run is `interrupted` and is never retried by itself. Whatever the list says, before any installer runs the checkout of this repository that holds the installers must be exactly at a release tag that verifies and have no changed tracked file (`verifyInstallerCheckout`, on by default; the failures are `installer_checkout_untagged`, `installer_checkout_dirty` and `tag_unsigned`, and nothing is copied or installed). The progress files are written through a temporary file with an unpredictable name that is created exclusively and without following a link, then renamed over the target. Settings (`fleet-update.json` beside the file): `signedTags`, `requireSignedTags`, `verifyInstallerCheckout`, `minFreeMb`, `minFreeMbServer`, `workspace`, `root`, `backups`, `owner`. `tools/make_fleet_sudoers.py` writes the rule of sudo for the account of the server: one line per command the tool issues, with the exact words and no wildcard (the check proves that every command the tool passes to sudo is one of its lines); the installers run as root.

**Nothing is to be built on the device (built and checked on the host and in GitHub Actions; not tried on a CM5).** The manual workflow `Component package` (`.github/workflows/component-package.yml`) builds the newest release of one program of the device, or of all of them, on an arm64 runner whose C library is older than the one of Debian trixie: the Rust and Go programs, the web pages, the server with its Node libraries and the Python programs with the libraries they declare. Each `hydra-<component>-<version>.tgz` carries its systemd units and `hydra-install.json`, is loaded from what it carries with no site packages (`tools/package_smoke.py`) and gets a provenance attestation. It is signed on the maintainer's machine (`tools/package_component.py sign`) and attached to the release of the program. Not covered: the industrial gateway stack (Docker Compose), the kiosk, the Wi-Fi setup, the splash screen and the base setup of the machine.

**The root helper (off by default).** `tools/root_helper.py`, started by `hydra-umc-helper.path` when the server leaves a request, installs those packages as root with `tools/package_install.py`: no checkout, no installer, no rule of sudo and nothing compiled. It only takes the newest release of each installed program, never an older version, verifies it with the key it was installed with, keeps the release and the units in use, restarts only the units that were running, checks health route and journal and goes back by itself; a program installed the old way is moved under `/opt/hydra-umc/.components/` with its data on its first update. Settings in `/etc/hydra-umc/helper.json`: `enabled` (false), `requireTotp` (true), `allowFirstInstall` (false), `planValidMinutes` (15), `healthTimeoutS` (40), `minFreeMb` (800). Applying and going back name the identifier of the last look and bring a one-time code (`root_helper.py totp-enroll`, secret in `/etc/hydra-umc/helper.totp`). It replaces `hydra-umc-fleet.path`: both are never active together. First installation: `provisioning/install_root_helper.sh <hydra-helper package> --apply --enable-trigger`. A server and a Studio that send the identifier and the code are needed to apply from Studio.

**What stops a program, and what does not.** A checkout whose only changes are `package-lock.json` files does not stop it: they are put aside with `git stash` (setting `stashLockFiles`) and can be seen with `git stash list`. A release that needs a newer `rustc` than the device has is left alone (`needs_newer_rustc`) before anything is touched. Programs with their own stack (kiosk, Wi-Fi setup, splash screen, the base of the CM5, the industrial gateway, the MQTT broker, the MTConnect adapter and the OPC UA server) are not updated by this tool, and a stopped service is skipped unless the run asks for inactive ones.

**What the rule of sudo is worth.** The rule has no wildcard, but each installer it names lives in a checkout that belongs to the account of the helper (`hydra-umc`, home folder `~/hydra-umc`). That account can rewrite those files, so the rule is root without a password for that account: treat `hydra-umc` as root-equivalent (keep it for the operator, no password logins from the network, no shared use). The isolation that holds is the one between the account of the server (`hydra-umc-server`: no sudo, no capabilities, no view of `/home`) and `hydra-umc`: the server can only leave a small request file that is cut down to fixed fields, and the settings of a request never come from its folder. The check of the tag of the installers' checkout before every run (above) narrows what a published release can do to the device; it does not make the account unprivileged. Running the installers from a copy owned by root, made from a verified tag, would close the gap for the installers but not for the programs they build from the checkouts of the same account, so it is not done yet. A program that runs from its link (`component_links.py`) is not touched by its installer, which would write into the release in use: with `usePackages` on (off by default) it is updated with the signed package of its release (`hydra-<name>-<version>.tgz`, `.sha256` and `.sig` from the same release, fetched only from github.com; `package_component.py verify` checks hash and signature; `deploy_release.py install` keeps the release in use, switches, restarts and goes back by itself; the checks of version, unit, health and journal run after it and, if they fail, `deploy_release.py rollback` puts the earlier release back); with it off, or for a program whose release carries no package (only `server`, `studio`, `os-agent`, `twin` and `orchestrator` have a layout), it is left alone and the plan says why (`migrated_needs_packages`, `migrated_no_package`). The restart is the `restartCommand` of `<components>/deploy.json`, for example `sudo -n /usr/bin/systemctl restart hydra-umc-{component}.service`, with the matching line in the rule of sudo (the unit of the OS agent is `hydra-umc-agent.service`). The Studio of a server updated by package comes in its own package. Nothing here restarts the machine. It has not run on a CM5; `tools/verify_fleet_update.py` proves it on a simulated device.

**The isolated server asks a helper instead of running the tool (`fleetUpdate.helper`, off by default; built and checked on the host only).** The unit of HYDRA-UMC-SERVER runs as its own account with `NoNewPrivileges=true`, no capabilities and `/home` hidden, so a child of it can neither find the checkout of this repository, nor call `sudo -n`, nor use the git configuration of the account that holds the signing keys. Nothing of that isolation is lowered. `provisioning/install_fleet_helper.sh [--user ACCOUNT] [--workspace DIR] [--signers FILE] [--enable] [--apply]` installs the other half: `systemd/hydra-umc-fleet.path` watches ONE file, `/opt/hydra-umc/server/data/fleet-update/request.json`, and starts `systemd/hydra-umc-fleet.service`, a oneshot unit that runs `fleet_update.py request --state ... --request ... --config /etc/hydra-umc/fleet-update.json` as the account that owns the checkouts (default `hydra-umc`, group `hydra-umc-server`, `UMask=0007`) and that has the rule of sudo written by `make_fleet_sudoers.py` (default workspace `/home/<account>/hydra-umc`). The shared folder `fleet-update` is owned by the server, mode `2770`, so the two accounts share the progress file, its heartbeat and the answer and nobody else sees them. The request is `{"v":1,"id","command":"plan"|"run"|"resume","names":[...]}`: the tool opens it without following a link, takes it away at once, refuses anything longer than 4 KiB, anything with another field value than the patterns of a program name (`resume` names exactly one), and writes the answer `{"id","command","exit"}` to `<state>.done`. Its settings come from `--config` (root-owned), never from `fleet-update.json` beside the progress file, so a request cannot relax the signature check. `allowedSigners` (default `/etc/hydra-umc/allowed_signers`, installed by `--signers`) is passed to `git verify-tag` when the file exists, so the result does not depend on the git configuration of the account that runs the tool. `make_fleet_sudoers.py` no longer assumes a home: without `--workspace` it uses `/home/<user>/hydra-umc`. The helper does nothing until the server's configuration has `"fleetUpdate": { "helper": true }` and the switches of the update (`updateCheck.enabled`, `maintenance.enabled`). `tools/verify_fleet_update.py` goes from 43 to 50 cases (a request to look, to run only the programs it names and to take one up, twelve kinds of request that are refused without a single command, a request behind a link, the settings that never come from the folder of the server, the signers file, and one check that the units, the installer and the rule of sudo name the same account, files, group and folder). Not run on a CM5.

**Units that run from the release in use, built and checked on the host only, off by default.** `tools/component_links.py` (`status`, `migrate`, `unmigrate`) turns `<root>/<name>` (where the unit points today) into a link to `<components>/<name>/current`, the layout of `deploy_release.py` (`releases/<version>-<n>`, `state.json`), so that the signed packages can replace a program and put the earlier one back without changing a path. What the program writes (`data`, `models`, `workspace`, or the folders of `stateDirs`) lives once in `<components>/<name>/state/` and is linked inside every release (`stateDirs` in `deploy.json`; empty by default, so nothing changes for a package installed without it). Nothing happens unless `<components>/wiring.json` says `"enabled": true` and the call has `--apply`; without `--apply` it says what it would do. `migrate` stops the program, moves its state, copies the program into the first release, puts the links in place, starts it and checks it, and puts everything back by itself (status 3) if it does not stop, start or answer; the old folder is kept as `<name>.premigration`, never deleted. `unmigrate` is the way back by hand and carries back what the program wrote since. `tools/verify_component_links.py` proves it in temporary folders: off by default, the dry run, the data kept once, a signed package installed and gone back from without touching the data, each failure, the way back and every refusal. A fix found on the way: the `current` link of `deploy_release.py` pointed beside `releases/` and not into it, and could not replace itself on a host that cannot rename a link over a link. It has not run on a CM5, and the units and installers still write to `<root>/<name>`: the installers of the checkout flow would write into the release in use through the link, so the two flows must not be mixed on a program that has been migrated.

**Two slots, built and checked on the host only.** `provisioning/ab_slots.py` is the state machine of a
two-slot (A/B) system image: an image is written to the idle slot after its SHA-256 matches, the boot
loader is asked to try it once (the Raspberry Pi `tryboot` entry of `autoboot.txt`), and the new system has
a time limit to report healthy. Only a healthy report in time (`confirm`) changes the default boot entry; a
late or missing report, a slot that never started, or a board that fell back to the old slot marks the tried
slot bad until a new image is written to it, so a bad image can never become the default. It decides and
records; a backend carries the decision out (`SimulatedBackend` for the checks, `AutobootBackend` for the
text of `autoboot.txt`), and it never runs `dd` or `reboot` itself. Every command that changes something is
refused unless `HYDRA_UMC_AB_SLOTS=1` is set (off by default), and a damaged state file is refused, not
repaired. `tools/verify_ab_slots.py` proves it with both backends and a seeded random walk. The image
builder does not yet produce two-slot images, no installer or unit calls it, and it has not run on a board:
that needs a CM5 with a boot loader that supports `tryboot_a_b`.

Firmware retains its own tested update and recovery process. Do not couple a
Raspberry Pi OS upgrade to a firmware change without a maintenance plan.
